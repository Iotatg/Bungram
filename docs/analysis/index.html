关键分界：rea 有两条完全独立的通道。 原生通道吃 .so/.exe（Ghidra/IDA/Hopper），Android 通道吃 .apk（jadx）。 rea analyze apk/telegram.apk 会直接报 target_unsupported——它压根不认为 APK 属于自己。 这也是为什么 8 条 Android 命令虽少，却覆盖了 90% 的实际需求。

移植路线 P1–P6

P1消息真正走服务端
把 MessagesScreen 的 demo 源换成 MessagesRepository，新增 MessagesPresenter。验收：断网重连不丢消息。
P2离线队列（抄 Signal）
新建 data/queue/OutboxWorker.kt，先做 12 个 job，Room 持久化。验收：飞行模式发 5 条，恢复后按序送达。
P3本地库（抄 Telegram 表结构）
Room：messages(id, chat_id, seq, sender, kind, ciphertext, state, ts) + FTS4。验收：1 万条冷启动 < 300ms。
P4E2EE（抄 Signal 协议，不自研）
引 libsignal-client，crypto/SessionStore.kt，密钥状态机照 SecretChatHelper。验收：服务端抓包无明文。
P5媒体管线
media/Uploader.kt 分片 + 断点续传 + 缩略图。验收：50MB 视频弱网可续传。
P6通话
WebRTC + 信令复用 WS；权限只加 4 个。验收：1:1 通话 3 分钟不崩。

诚实清单

1. Telegram APK 已混淆（类名 a.a），类级取证只能靠源码仓库。
2. Signal 全量类清单首次并发执行失败（三个 JADX 抢内存），单跑 + 前缀过滤后成功：7,346 / 22,008。
3. apktool 只解出 105 条 string 资源 —— Telegram 文案在 LocaleController 里，不在 strings.xml。
4. 没有真机，组件 exported 行为、后台限制、厂商角标均未实测。
5. 权限按短名归类，少数自定义权限落入 other，已在报告 §2.3 单列。
